# 网易云 → iPod 同步方案

> 目标：把网易云音乐的歌单/喜欢的歌下载并同步到 iPod Classic
> 涉及仓库：`source/repos/ipod-cli`（导入引擎 + 同步器）、`source/repos/api-enhanced`（网易云 API）
> P0 调研完成：2026-09-19 ｜ **结论：技术全通，覆盖率 99%**
> **方案已定**：音质在前端可选，默认 `exhigh`（320k）；前端只做四块，不做完整客户端

## 一句话

网易云 API 能拿到 99% 的歌曲下载链接，技术上完全可行。
容量问题不靠"事先算好分配"，而是**把音质做成前端设置项**——默认 320k（全库 40 GB 装得下），
需要时按歌单升到无损。

### 1.3 ★ 档位陷阱（重要经验）

**不要"从最高档往下试"，那会拿到一堆空间音频。** 逐档实测：

| 请求档位 | 实际返回 | 单曲大小中位 | 对 iPod |
| --- | --- | --- | --- |
| `standard` | 128k MP3 | ~3 MB | ✅ 可用但浪费 |
| `exhigh` | 320k MP3 | 5–13 MB | ✅ 直接可播 |
| **`lossless`** | **FLAC 568–1191k** | **25 MB** | ✅ **正解，转 ALAC** |
| `hires` | 不稳（有时真 hires，有时退化成 lossless） | 29–45 MB | ⚠️ 24bit，不建议 |
| `jymaster` | 少数真母带，多数退化成 jyeffect | 108 MB | ❌ 24bit+ |
| **`jyeffect`** | **空间音频** | **78.6 MB** | ❌ **iPod 完全不支持** |

按 jyeffect 全下的话，5906 首要 **455 GB**。

**结论**：探测/下载档位阶梯固定为 `[lossless, exhigh, standard]`。

## 二、网易云给的文件是"半成品"

| | 320k MP3 | 无损 FLAC |
| --- | --- | --- |
| 标签 | ✅ 完整（title/artist/album/track/date/**label**） | ❌ **一个字段都没有** |
| 内嵌封面 | ❌ 无 | ❌ 无 |

**必须自己补全**，两条都实测可行：

1. **标签**：从 `/song/detail` 取 `name`/`ar[].name`/`al.name`/`no`，用 mutagen 写入。
2. **封面**：`al.picUrl` 加 `?param=600y600` 得到 600×600 JPEG（约 476 KB），
   内嵌为 FLAC 的 `PICTURE` 块（type=3 Cover front）。

验证通过：补完后 ipod-cli 现有的 `read_pc_track` 能正确读出全部字段，
且 `has_embedded_artwork=True`——**说明可以直接喂给现有的导入管线**。

## 三、顺手发现的 bug（ipod-cli）

**24bit FLAC 转出来的是 24bit ALAC，iPod Classic 播不了。**

| | 码深 | 大小 |
| --- | --- | --- |
| 源 FLAC | 24bit | — |
| 现有转码产物 | ❌ 24bit ALAC | 43.5 MB |
| 加 `-sample_fmt s16p` | ✅ 16bit ALAC | **22.5 MB** |

修法：`transcode.py` 的 `build_ffmpeg_command` 加 `-sample_fmt s16p`。
**顺带体积减半**——这对容量紧张的场景很关键。

## 四、运维坑（都踩过了）

### 4.1 api-enhanced 部署

```bash

npm install --omit=dev --ignore-scripts   # ← --ignore-scripts 跳过 husky（dev 依赖）

```

也可以用 npm 包 `@neteasecloudmusicapienhanced/api` 或 Docker 镜像 `moefurina/ncm-api`。

### 4.2 首次启动会报 `xeapi public key is missing`

**这不是致命错误**。xeapi 公钥的注册本身依赖匿名 token，形成了先有鸡还是先有蛋：
第一次启动时注册失败（打印错误但被 catch），公钥已写入
`%TEMP%/xeapi_public_key`；**重启一次就正常了**。

### 4.3 ★ node 在 MSYS 后台跑不起来

`terminal(background=true)` + `node xxx.js` 会以 `stdin is not a tty` 立刻退出
（最简单的 `node -e` 也复现）。**必须用 PTY 模式**（`pty=true`）。
python 脚本没这个问题。

### 4.4 限速表现为"返回成功但数据为空"

批量拉歌单时会被限速：HTTP 200、`code=200`，但 `songs` 是空数组。
**不能当成"这个歌单是空的"**——必须退避重试。
第一次跑全库就因此漏了 2184 条（4468 vs 正确的 5906）。

### 4.5 艺人的 name 可能是 null

`ar[].name` 有时是显式 `null`，直接 join 会抛 `TypeError`。要 `(a.get("name") or "")`。

### 4.6 登录信息（含 cookie）绝不能进 git

存在 `ipod-cli/.ncm/p0-state.json`，已加入 `.gitignore`。
登录用扫码（`login_qr_key` → `login_qr_create?qrimg=true` 拿 base64 二维码
→ 轮询 `login_qr_check`，803 表示成功并返回 cookie）。
**账号是 VIP（vipType=11）**，这是能拿到无损的前提。

## 五、已定方案（2026-09-19）

### 5.1 音质：前端可选，默认 `exhigh`

不事先固定"哪些歌用无损"，而是把**音质做成设置项**：

| 选项 | 说明 |
| --- | --- |
| `exhigh`（**默认**） | 320k MP3，全库 40 GB 装得下，免转码 |
| `lossless` | 无损 FLAC → 转 16bit ALAC，体积约 3.5 倍 |
| `standard` | 128k，仅在极端省空间时用 |

对 iPod 无意义的档位（`hires` / `jymaster` / `jyeffect`）**不在选项里**——
它们要么 24bit+ 要么是空间音频，iPod Classic 播不了，放上去只会踩坑。

### 5.2 前端范围：不做完整客户端

只保留四块，全是"为了把歌弄进 iPod"这条主线服务的：

| 模块 | 职责 |
| --- | --- |
| **歌单浏览** | 列出歌单 / 我喜欢的音乐（**核心用途是拿到"要下载什么"的清单**） |
| **下载器** | 下载状态、进度条、失败清单 |
| **本地音乐管理** | 管理 iPod 上的歌曲（增删查，复用现有 `remove` / `list` / `verify`） |
| **设置** | 音质选择（默认 exhigh）、登录状态 |

明确**不做**的：完整播放器、歌词、评论、搜索发现、社交——那些是网易云客户端的事。

### 6.6 P2 踩到的三个坑（都很隐蔽）

**① 状态库不区分设备，彩排污染真机规划**
彩排把歌记成"已同步"，真机同步时被误判成"已在设备上"：显示"要写入 0 首"
（其实要写 3 首），播放列表算成 6 个成员（3 个是指向不存在曲目的幽灵条目）。
那 3 个最后靠写入器按 `valid_db_track_ids` 丢弃了，所以设备没坏——
**但"靠下游兜底"不该是设计**。
修法：`synced_on_device()`——状态库说"已同步"的歌，必须拿 iPod 上**实际存在的
文件位置**核对一遍。**状态库只是加速，设备才是真相。**

**② 没有新曲目时播放列表写不进去**
`execute_import` 在"没有需要导入的新曲目"时会提前返回，于是只更新歌单成员
（或只是重跑一次保持最新）时什么都不写，而 `verified` 还是默认 False，
报出一个**假的**"读回校验未通过"。实测踩到：设备 9 项全绿，push 却报失败。
修法：无新曲目但有列表要写时直接走 `dbwrite.write_library`。

**③ 状态库 db_track_id 溢出**
iPod 持久 ID 是随机 64 位**无符号**数，SQLite INTEGER 是**有符号**的——
真机 118 首里 61 首超 2^63-1，直接 `OverflowError`。
而且它发生在**写库成功之后**记录状态时，报错文案写死"数据库未被修改"
会误导人以为啥都没发生。修法：TEXT 存储 + 读出转 int + 版本迁移。

### 7.2 架构

```

   ↕ HTTP 127.0.0.1:8765
Python FastAPI (src/ipod_web/) ← 路由 + 单线程作业队列 + 缓存

### 7.3 ★ 核心：把「绝不并发」落成架构

`JobManager` = **一条队列 · 一个工作线程 · 全局串行**。
界面上连点十次下载，实际只有一个请求在飞。

* 网易云高频请求会风控封号
* iPod 那边两个作业同时重写同一个 iTunesDB 是**数据损坏级**风险

测试守着它：8 个线程同时提交，观测到的最大并发**恒为 1**。

**取消是协程式**的：`JobCancelled` 故意继承 `BaseException`——
作业体里到处是"这一首失败不要紧"的 `except Exception` 兜底，
取消要是普通 Exception 就会被吞掉，用户点了取消程序还在闷头下载。

### 7.4 ★ 最阴的坑：iPod 的持久 ID 是**无符号** 64 位

真机 118 首里 **61 首**的 `db_track_id` 超过 2^63-1。

* SQLite 的 INTEGER 是**有符号**的 → 状态库里存 TEXT
* JSON 数字交给 Dart → Dart 的 `int` 也是**有符号** 64 位，
  会**静默**溢出成负数，然后删除操作删错歌

所以 `db_id` 全程走字符串。写测试时 Dart 直接拒绝编译
`18446744073709551000`（"can't be represented in 64 bits"）——
这个编译错误本身就是最好的证明。真机实测曲目 ID：
`16977498299404266438`。

### 7.5 ★ 破坏性操作的防线

* **先预览再执行**，而且做成了**结构性保证**而不是界面自觉：
  预览返回一次性令牌，执行删除必须带上它。
  无令牌 / 伪造 / 重放 / 与预览内容不一致 / 过期 —— 5 种情况全拦。
* **预览数字必须等于实际**（预览说删 23 首，实际就得删 23 首）。
* **「全选本页（N 首）」和「全选筛选结果（M 首）」是两个按钮**，
  各自写明数量。合成一个"全选"的代价是**真删歌**。
* **清空曲库硬拦**（remover 本来就拒绝）。
* **界面里没有导出入口**（版权风险），但 CLI 的 `ipod export` 保留。

### 7.6 前端踩的坑

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| `file_selector` 要开发者模式 | 原生插件构建需要符号链接权限（要管理员） | 改用 PowerShell 的 `OpenFileDialog`，系统自带零前提 |
| .cpp 里的中文 | MSVC 按代码页 936 读源文件，报 C2001/C4819，看着像语法错 | 那个文件保持**纯 ASCII**，标题用 `\u` 转义 |
| 窗口开在屏幕外 | 截图看着"被截断"，实际是**截图工具 DPI-unaware** 只抓了虚拟化区域 | 截图脚本先 `SetProcessDPIAware()`；**先量再改**（GetWindowRect） |
| 杀进程杀不干净 | `uv run` 是两层的，杀启动器不杀 uvicorn，端口被占日志被锁 | `taskkill /T /F` 杀整棵树 |
| 操作条溢出 | 768px 宽下 RenderFlex 溢出 127px | 主操作固定最右 + 次要控件横向滚动 |

### 7.7 后端子进程的两条经验（实测）

1. **强杀应用会让后端变孤儿**（Dart 的清理钩子跑不到）。所以启动时
   **先探测、能复用就复用**——孤儿后端下次启动会被自动接管，不撞端口。
   实测：强杀 → 重启应用 → 复用成功（PID 不变）。
2. **调试面板是自动拉起后端的配套**。没有它，出问题只能猜。
   日志用 `?since=<seq>` **增量拉取**；挂在 root logger 上的缓冲要先
   把 `iopenpod.*` 压到 WARNING，否则解析器的 INFO 会刷屏。

### 7.10 歌单页的批量选择（2026-09-20 补齐）

方案 §4.1 里写了的，第一轮漏做了（只做了音乐库页的多选）。现在补上。

**能干什么**

* 每首歌前面有勾选框，勾几首就处理几首（`下载选中的 N 首` / `同步选中的 N 首`）
* 状态筛选：全部 / 未处理 / 已下载未同步 / 已在 iPod
* **「一键选中所有未处理的（N 首）」**——246 首要手点 246 次是不可接受的
* 选择**跨页保持**（50 首一页），翻页不清空
* `同步整个歌单` 单独一个按钮，跟"选中的"分开

**两个"看起来一样其实完全不同"的地方**

| 写法 | 含义 | 搞错的后果 |
| --- | --- | --- |
| `song_ids` 不传（null） | 整个歌单 | — |
| `song_ids = []` | **报错**："没有选中任何歌曲" | 当成整单的话，用户全取消勾选后一点，几百首开始跑 |
| `only_ids = None` | 不过滤 | — |
| `only_ids = set()` | 一首都不选（空计划） | 当成"不过滤"的话同上 |

空列表**绝不能**等价于"全部"。这个区别写进了后端、引擎和两边的测试。

**「一键选中」为什么必须走后端**

曲目是**服务端分页**的（50 首/页）。只在客户端勾的话，"全选未处理的"
实际只勾到当前页那 50 首——用户以为 243 首都在跑了，其实只下了 50 首。
所以加了个 `/api/playlists/{id}/ids?status=` 轻量接口：只返回 ID，
曲目本来就缓存在后端，**不产生任何网易云请求**。

**过滤放在取源曲目时，不是规划之后**

`fetch_source_songs` 拿到歌单曲目本来就得整份取回来（不然不知道歌单里有什么），
在源头按 `only_ids` 筛掉不影响请求数，却让后面的 `limit` / "已就绪"判断
全部作用在正确的集合上。而且顺序跟着**歌单原序**走——选中集是 set，
没有顺序，直接遍历的话下出来的顺序是随机的。

**顺手修掉的两个真问题**

1. 作业提交后那个"5 秒后自动刷新"原本用裸 `Future.delayed`——页面在倒计时里
   被销毁的话，树都拆了它还会去碰状态（测试直接报 "A Timer is still pending
   even after the widget tree was disposed"）。改成可取消的 `Timer` + dispose 里 cancel。
2. 操作条在窄窗口下把次要按钮裁进横向滚动区，测试点空。
   测试视口改成接近真实窗口（1600×1100）——窄屏可滚性由音乐库页的测试覆盖。

**测试**：Python 467 → **484**；Flutter 22 → **36**。

### 7.11 下载页改版 + 导出诊断记录（2026-09-20）

**下载页从"调试视图"改成"下载视图"。**

原来那一页是"左作业队列 + 右日志"——那是设置页调试面板该干的事。
现在只回答两个问题：现在在干什么、刚才干了什么。

* 当前任务卡：进度条、`42 / 246`、百分比、正在下哪首、还需多久、取消按钮
* 歌曲清单：每首带状态（✓ 已下载 / ✗ 失败 / 下载中 / 等待）+ 大小
* **失败的那首连原因一起显示**——"有 3 首失败"这种话对排查毫无帮助
* 只显示"下载歌"那一类作业；备份/健康检查/环境自检不混进来
* 排队时提示"前面还有 N 个任务"，但不出列表

**为此加的底层支持**

| 加的 | 为什么 |
| --- | --- |
| `execute_downloads(on_song=...)` + `SongEvent` | 界面要的是结构化的"哪首歌、成没成、多大、为什么失败"。让界面去 parse `✓ [3/246] 歌名 → 7.2 MB` 的话，改次措辞就坏，歌名里带数字（《7/11》）还会被认成进度 |
| `Job.items` | 逐首歌的记录。**按 index 整个 dict 换掉**而不是就地改字段——工作线程在写、HTTP 线程在读，就地改会读到半截状态；`to_dict()` 出去前再复制一份 |
| `/api/jobs` 列表**默认不带 items** | 20 个作业各带几百首明细、每 3 秒轮询一次 = 每轮几百 KB 纯浪费，而界面一次只看一个。只给"最新的"+"正在跑的"那个带，详情接口照旧带全 |

**导出诊断记录**

下载页和设置页调试面板各有一个入口。`POST /api/debug/export` 写一份
完整现场到「文档」目录，返回绝对路径。

内容是排查时真正需要的东西：环境（Python/ffmpeg/路径/版本）、
设置（音质/间隔/缓存/账号）、设备、**每个作业干了什么**（状态/耗时/
结果/逐首歌成功失败与原因）、带时间戳的完整日志。

三个刻意的决定：

1. **不走作业队列**——用户往往正是卡在某个作业上才来导出的，
   排在它后面就永远导不出来。
2. **写 UTF-8 带 BOM**——Windows 记事本按本地代码页猜编码，
   没 BOM 中文全是乱码，导出的东西看不懂就白导了。
3. **写「文档」目录**而不是仓库里的 `.ncm/`——太隐蔽的话用户找不到文件。
   界面上显示完整路径 + 「复制路径」「打开所在文件夹」。

实测导出（真机跑了一次 2 首的下载之后）：

```

**顺手修掉的真问题**：导出按钮在对话框开着的时候一直转圈
（`_exporting` 要等对话框关掉才复位）——测试里表现为 pumpAndSettle
永远等不到稳定，真实界面上就是"对话框开着按钮一直在转，像没导完"。

**工具坑**：`patch` 写 CRLF、`write_file` 写 LF。同一个文件被两种工具

### 7.12 下载页加「本地已下载」管理；音乐库改名（2026-09-20）

**下载页的定位被我理解错了。** 它不只是"这次下了什么"，还管
**电脑上已下载的音乐**。现在拆成两个标签：

| 标签 | 管什么 |
| --- | --- |
| **本次任务** | 当前/最近一次下载的进度，逐首歌的结果（含失败原因） |
| **本地已下载** | 电脑上那份缓存：搜索、排序、多选删除、全选筛选结果 |

界面上写明了"iPod 上已经同步过去的歌不受影响，删的只是电脑上这份下载缓存"——
不说清楚的话用户会以为"删了就没了"而不敢清。

**音乐库 → iPod 音乐管理。** 那个页面是 iPod **设备上**的 iTunesDB
在界面上的样子，叫"音乐库"容易跟"电脑上的音乐"混。现在两页的说法分明：
**iPod 音乐管理删了是真从 iPod 上删歌；下载页删的只是电脑上这份。**

#### 为了显示歌名，动了数据库（schema v2 → v3）

`downloads` 表原本只有 song_id/path/level/size，界面要列歌名就只能
挨个读文件标签——几百首就是几百次磁盘解析。加了 `name` / `artist`：
下载的时候顺手记下来。

**`CREATE TABLE IF NOT EXISTS` 只保证表存在、不会改已存在表的列**，
所以必须显式 ALTER。迁移用 PRAGMA 先查列、幂等；老记录的名字补不上
（当初就没存），界面显示"（未知曲目）"，重新下一次就有了。

真机验证：真实库 v2（6 条、无新列）→ 打开后 v3，列加上、6 条一条不少。

#### ★ 删文件那条路里的陷阱

最初想用 `glob(f"*{song_id}*")` 去缓存目录找文件。**这会删错歌**：
song_id=123 会把 1234 的文件一起匹配进来。

正确做法：先用 `cached_download` 拿到记录里存的**确切路径**
（顺带核实文件真的在），再删记录，最后删文件。
先删记录再删文件的顺序也是刻意的——反过来中途失败会留下
"记录说文件在、其实不在"的幽灵条目。

#### "空列表"永远不是"全删"

`POST /api/downloads/remove` 收到空 `song_ids` **报错**，不是全删。
当成全删的话，用户点了个没勾选的删除就把整份缓存清了。
清空有专门的按钮。同一个约定在歌单页的 `song_ids` 也用了。

#### ★ 一个真机才暴露的致命 bug：批量替换改出了自递归

给 `BackendService` 加 `_notify()` 包装（为了让退出时的日志不再通知
已销毁的对象）时，批量替换把 `_notify()` **自己内部**那行
`notifyListeners()` 也换成了 `_notify()` → 自递归 → 爆栈。

表现：应用起来了但后端没被拉起、界面卡在启动页。**测试全绿**——
因为测试里从没走到"活着的时候发通知"这条路径。
加了 `backend_service_test.dart` 守住它。

教训：批量替换之后要回头看一眼**被替换的那段代码本身**，
别只看替换结果对不对。

#### 真机验证

```
迁移：v2（6 条、无新列）→ v3（列加上、6 条保留）
列表：8 首 / 60.8 MB，按体积排序正确
新增：遇见 (DJ版) / TieZ、十年（DJ版）/ T.G.A.阿航 —— 名字都记上了
删除：8 个文件 → 7 个，删的正是选中的那首（STAY）
```

**测试**：Python 494 → **518**；Flutter 49 → **62**。

### 7.13 自动刷新 / 来源分组 / 右键菜单（2026-09-20）

#### 自动刷新：不再靠拍脑袋等几秒

下载、同步、删除、导入都走后台作业队列，提交完立刻返回。作业**真正干完**
时页面数据已经过期了。以前每个页面自己写定时器猜（歌单页等 5 秒、
下载页等 4 秒），既不准又互相不同步。

现在 `AppState.refreshSignal` 统一管：轮询发现**完成集合里出现了新的作业 id**
就 ping 一次，三个页面一起重新拉。

判据用"新完成的 id"而**不是**"队列从忙变闲"——后者会漏掉两次轮询（3 秒）
之间就干完的短作业。删几首本地文件正是这种：用户看不到列表更新，
会以为没删掉。

#### 本地音乐按来源歌单分组

下载页「本地已下载」左栏 = 来源歌单，右栏 = 曲目，跟网易云歌单页、
iPod 音乐管理页同一个结构。

- `downloads` 加 `source_kind` / `source_playlist_id` /
  `source_playlist_name`（**schema v3 → v4**）
- **按整数 id 归组、用名字显示**：歌单改名后刷新一下就对
- `source_key` 是**字符串**（`liked` / `unknown` / `playlist:123`）：
  "我喜欢的音乐"的 playlist_id 也是 0，跟"老记录没来源"撞，只用数字会合并
- 老记录归到「未记录来源」单独一组
- 分组数据按**全部**记录算，**不跟着筛选变**——跟着变的话切进去就切不回来
- `/api/downloads/ids` 也带 source：在 A 歌单点「全选筛选结果」不能选上 B 的
- 换来源**清空勾选**：跨来源留着勾选会删到用户看不见的歌

#### 右键菜单

三个列表的每行都能右键，共用 `widgets/context_menu.dart`。

约定：不可用的项**留在菜单里但置灰 + 写明原因**（不显示的话用户以为功能没有）；
删除类标红且**仍要弹完整确认**（菜单最容易误点，"点了一次"不等于确认过）。

实现细节：
- `_start` / `_remove` 加 `onlyIds` 参数，而不是临时改界面勾选状态
  （改状态有副作用：操作条冒出来、勾选被清）
- **踩到一个真 bug**：iPod 音乐管理页的 `removeTracks` 原来传 `_selected`，
  加了"只删这一首"之后就错了——**预览的是 A、删的是 B**，T4「预览==实际」
  直接破掉。改成传跟预览同一份 `ids`。

#### 一次数据消失的调查（值得记）

真机验证时发现 `.ncm` 的下载记录从 **7 条变成 2 条**。查证过程：

1. 消失的 5 条 = 最早那 6 条（v2 备份可查）里，除我测试删掉的 STAY 之外的全部
2. 5 条**都是没有名字**的（界面显示"（未知曲目）"）
3. 全代码库里能删记录+文件的路径只有两条：`POST /api/downloads/remove`
   （只删传进来的 id）和 `POST /api/cache/clear`（清空）
4. 5 条留下来 2 条 → 只能是 `remove` 带着这 5 个 id 被调用过
5. 排除测试：所有打删除接口的测试都用 `tmp_path`（`web_ctx` 显式传了
   `cache_dir`），跑测试前后对真实 `.ncm` 没有任何改动

结论：**有人在界面里选中那 5 条"（未知曲目）"删掉了**，不是代码自动删的。

但顺带发现一个**真隐患**：`WebContext.cache_dir` 的默认值是**相对路径**
`.ncm/cache`，而 pytest 的 cwd 就是仓库根目录。哪个测试忘了传 `cache_dir`
又恰好打了 `/api/cache/clear`，删掉的就是用户真实的下载缓存，**而且静默无声**。

→ 在 conftest 加了 session 级的保护：跑测试前后对一遍真实的 `.ncm/`，
被动过就报错（列出新增/删除/改动）。一次 listdir 换一个响亮的失败。

### 7.14 修「删了本地的歌重新下载，提示已准备就绪」（2026-09-20）

**用户报的**："我把本地的歌删了重新下载，它提示已准备就绪。"

#### 根因：把两件不同的事当成一件

`plan_sync` 里只有一条跳过规则：`if song.id in synced: 跳过`。
但"同步到 iPod"和"下载到本地"要的**完全不是一回事**：

| 用户点了什么 | 他的意思 | 正确的跳过条件 |
| --- | --- | --- |
| 同步到 iPod | 让 **iPod** 上有 | 设备上已经有了 |
| 下载到本地 | 让 **电脑** 上有 | 本地文件已经在 |

于是：删掉本地文件 → 点「下载」→ 因为歌还在 iPod 上、全部被跳过 →
一首都不下。界面把这件事翻译成「选中的曲目都已经就绪，没有要处理的」。

**修法**：加 `TARGET_IPOD` / `TARGET_LOCAL` 两个目标，跳过条件分开。
默认 `TARGET_IPOD`，CLI 与既有调用方不受影响。

#### 同族缺陷（一起扫掉的）

共同点：**拿"记录"当"事实"，或拿"iPod 的事实"回答"本地的问题"。**

| # | 缺陷 | 修法 |
| --- | --- | --- |
| 2 | `push=False` 时 `library=None`，规划**退化去信状态库** `store.synced_ids()`（不分设备，彩排/别的机器的记录也算数） | `target=local` 时 `synced` 恒为空集——本地下载根本不该关心 iPod |
| 3 | 「已下载」徽标用 `downloaded_song_ids()`（**含文件已丢的脏记录**），而规划用 `cached_download()`（**核对文件**）→ 两边打架 | 徽标也改成核对文件 + 顺手清理脏记录（自愈） |
| 4 | `selectable => status != 'on_ipod'`——"在 iPod 上但本地没留"的行**根本不给勾**，想重下都选不中 | `!(onIpod && local)`：两边都有才是真的没事可做 |
| 5 | 我自己的保护网误报（比对整个 `.ncm/`，而应用自己会写 `.ncm/logs/`） | 只看 `.ncm/cache` 里**文件变少**，新增和改动一律容忍 |

#### 界面：两个维度分开说

行状态从"已在 iPod"改成按两个维度显示：`已在 iPod · 本地无` /
`已在 iPod` / `已下载` / `未处理`。后端每首歌多给 `on_ipod` / `local`
两个布尔，counts 多给 `on_ipod_but_no_local`。

跳过提示也不再只说"都已经就绪"，而是"没有要处理的：本地已下载 3 首"。

#### 真机复现

```
① 造场景：本地有文件 + 状态库记着"已同步"
② 删前规划 → target=local, needs_fetch=0, 跳过原因 {本地已下载: 1}   ✅
③ 删掉本地那份 → 文件没了，状态库的同步记录**没被动**             ✅
④ 删后再规划 → needs_fetch=1, to_download=1, 跳过原因 {} ← 会去下载
   （旧代码这里会因"状态库记着已同步"而跳过，就是"已准备就绪"）
⑤ 真跑下载 → 夏天的风 9946 KB 回到本地，来源记成 DJ                ✅
```

**测试**：Python 540 → **551**；Flutter 82 → **85**。

### 7.15 「我喜欢的音乐」的顺序；音乐库多选；清空拦截的措辞（2026-09-20）

#### 「我喜欢的音乐」：`/likelist` 的顺序不能用

`/likelist` 只保证"**有哪些歌**"，它返回的顺序是网易云内部存储的顺序，
对外不可解释。实测（用户 246 首）：

```
两者顺序一样吗：False
集合一样吗：    True      ← 歌是同一批
同位置相同的：  0 / 246   ← 一个都对不上
```

不是创建/更新时间、不是 id 升降序、也不是歌单顺序的倒序——**稳定但对不上任何字段**。
后果：iPod 里歌的排列跟用户在 App 里看到的完全是两回事。

| # | 工具原来的顺序 | App 里看到的 |
|---|---|---|
| 1 | STAY - The Kid LAROI | 虚拟 - 陈粒 |
| 2 | green to blue - Aurenth | 越来越不懂 - 蔡健雅 |

**改法**：走 `/playlist/track/all`（App 显示的顺序）。歌单 id 从歌单列表里
按 `specialType=5` 认——**不能按名字找**（用户把它改成了"被改过名的喜欢的音乐"）。
界面调用时把 id 一起带上（列表里本来就有），零额外请求。

**顺带省请求**：歌单接口自带元数据，不用再补一轮 `song/detail`：

| | 原来 | 现在 |
|---|---|---|
| 246 首 | likelist + 3×song/detail = **4 次** | **1 次**（实测 request_count=1） |
| 6000 首 | **61 次** | **6 次** |

`fetch_source_songs` 的 liked / playlist 两分支也随之合并成一条。
兜底：拿不到歌单 id 退回 likelist（顺序会不对，但有歌好过整个失败）。

#### 歌单列表的顺序（另一个问题）

后端/路由/Flutter **一层都没排序**，原样透传 `/user/playlist`。实测规律：

- **自建歌单**：按 `createTime` 倒序（新建的在前），"我喜欢的音乐"钉在第 1 位
- **收藏歌单**：createTime / updateTime 都对不上，是服务端的收藏顺序（接口没返回该字段）

潜在坑：`limit: 100` 且**不翻页**——收藏到 100 个以上会静默消失。

#### iPod 音乐库多选：点一个掉一个

`_onRowTap` 的普通单击走 `_selectOnly`（清掉其它只留这一首），是照文件管理器
的老习惯设计的。但行左边画的是**复选框**——用户看到方框就以为点一下是"勾它"。
而且**歌单页同一件事是累加的**，两页行为不一致。

改成单击 = 勾选/取消，跟歌单页一致；Shift 保留范围选。

#### 删到只剩最后一首删不掉

三层故意拦截（remover 两层 + `dbwrite.write_library` 一层），**用户选择保留**：

> 本工具不提供清空操作——删除是整库重写，写下去没法撤销，误点的代价太大。

但原来只有这一句，用户是在**逐首清理时**撞上的，会卡在那儿。
现在把替代做法一起给出来（Finder/iTunes「恢复 iPod」、设备上「抹掉所有内容和设置」）。
界面配套：409 这类"我们决定不做"的消息改用**对话框**（可读完、可复制），
不再塞进 4 秒就消失的 SnackBar。

#### 顺手修一条不严密的测试

`test_no_device_does_not_break_the_export` 是靠"跑测这台机器恰好没插 iPod"
过的——真机一插上就红，第一反应是"我改坏了什么"，白查一轮。
改成显式指定一个不存在 iPod 的路径。**测试不该依赖机器上插了什么硬件。**

**测试**：Python 551 → **557**；Flutter 85 → **87**。

### 7.16 「我喜欢歌单的顺序还是乱的」——同一套逻辑有两份实现（2026-09-20）

**用户反馈**：上一轮改成"走歌单接口拿 App 的顺序"之后，用户说**还是乱的**。

#### 根因：改漏了一份副本

取曲目的逻辑**写了两处**：

| 位置 | 用途 | 改了吗 |
| --- | --- | --- |
| `ipod_cli/ncm/sync.py::fetch_source_songs` | 规划 / 下载 | ✅ 上一轮改了 |
| `ipod_web/routes/playlists.py::_load_tracks` | **界面显示** | ❌ 漏了 |

于是出现最别扭的状态：**下载的顺序对了，界面上看到的还是乱的**。

```python
# 副本长这样（已删）
if source.kind == "liked":
    ids = client.liked_song_ids(...)      # ← 顺序还是内部那个
    tracks = client.song_details(ids, ...)
```

**改法**：`_load_tracks` 直接调 `fetch_source_songs`，不再自己实现。
同一套逻辑有两份实现，就必然有一份会掉队。

顺带清掉第三个副本：CLI 的 `ipod-sync playlists` 为了数"我喜欢的音乐有多少首"
单独发了一次 `/likelist`——歌单列表里本来就有 `track_count`。

现在 `liked_song_ids` 全项目只剩一处调用：`fetch_source_songs` 里**拿不到
歌单 id 时的兜底**。

#### 回归测试怎么守住的

`fake_with_playlists` 里把 likelist 的顺序**故意设成相反的**（`reversed`），
并给 `FakeNcmClient` 补上 `liked_playlist_id`。这样一旦哪条路又走回 likelist，
`TestLikedTracksOrder` 立刻红。

#### 真机验证（改后）

```
/api/playlists/10000000002/songs →
  1. 虚拟 - 陈粒        4. 大石碎胸口 - 万能青年旅店
  2. 越来越不懂 - 蔡健雅   5. Episode 33 - She Her Her Hers
  3. 我还年轻 我还年轻    6. 带我去找夜生活 - 告五人
与网易云 App 一致（改之前第 1 首是 STAY - The Kid LAROI）
```

#### 教训

**"两条路读同一份数据"的地方，验证要两条都走一遍。**
上一轮只验了 `plan` 接口（规划），没验 `songs` 接口（界面）——
等于只验了一半，缺口正好落在用户看得见的那一半。

### 7.17 同步失败「No artwork format definitions」——设备没注册给内核（2026-09-20）

**用户报的**：

```
ART: no artwork definitions available for device unknown at D:\;
     refusing to guess an unrelated device format
RuntimeError: No artwork format definitions are available for this iPod;
              cannot write ArtworkDB safely.
```

#### 根因

内核要"这台设备的封面格式定义"才敢写 ArtworkDB。格式从**设备能力表**推出来，
前提是内核知道当前设备是谁——它用 `get_current_device_for_path()` 查，
那个值由 `set_current_device()` 存。

日志里写得很明白：**`device unknown at D:\`**。真机实测对比：

| | 内核认为的设备 | 封面格式 |
| --- | --- | --- |
| 注册前 | `None` | `{}` → **拒绝写** |
| `device.activate()` 后 | iPod Classic / 6th Gen | `{1055, 1060, 1061, 1068}` |

**CLI 的同步路径调了 `activate()`（`sync_cli.py:479`），界面这条路一次都没调。**
conftest 里甚至早就有个 `active_device` fixture（注释写着"写封面需要"）——
说明这个要求一直知道，只是没接到界面这条路上。

#### 改法

放在 `WebContext.device()` 里统一注册：所有路由拿设备都走这里
（同步 / 导入 / 删除 / 状态 / 校验），一次修掉不会再漏。

顺带做成**幂等**：状态条每 3 秒轮询一次，不判重就每次都注册一遍，日志刷出
一大串 `Device stored: iPod Classic 6th Gen ...`——那份日志正是「导出诊断记录」
给人看的。实测从"每 3 秒一条"降到"启动时一条"。

#### 顺带发现：播放次数增量文件从不清理

`iPod_Control/iTunes/Play Counts` 是"iPod 上自上次同步以来积累的播放/跳过次数"
的**增量**文件：读库时被合并进曲目（libgpod 的 `get_mhit` 逻辑）、随写库落盘。
但**全项目没有任何地方写它或删它**——只有解析。

后果（真机实测）：

- 那份残留是 **2023-10-08** 的，库里早换过好几轮 → 每读一次库就重新合并一遍，
  日志里每 6 秒一条 `Track count (2) != Play Counts entry count (3)`
- 更糟：合并**按下标配对**（`entries[i]` ↔ `tracks[i]`），旧歌的播放次数会算到
  **新歌头上**，而且随写库**固化**下来

iTunes 的做法是同步完就清掉它。现在 `write_library` 在**读回校验之后、返回之前**
清掉——顺序关键：先让增量随本次写库落盘（吸收），再删文件。
测试专门守"吸收后清掉"而不是"丢掉"。

#### 真机验证

```
同步 3 首（DJ）      → added 1 / verified True，ART 不再报错
                      ArtworkDB + 4 个 .ithmb 写出，编号 1055/1060/1061/1068
同步 2 首（我喜欢的） → added 2 / verified True
Play Counts          → 已清；之后 45 秒零警告（修复前每 6 秒一条）
```

**测试**：Python 563 → **566**。

### 7.18 合并在线歌单与本地下载（2026-09-20）

**用户提出**："把在线歌单和本地下载合为一体，显示状态（未下载、已下载、已同步），
下载就只显示下载进度了。这样更加轻量、维护也更简单。"

#### 关键发现：主要是删

三态后端**早就在给**了（`SongRow.onIpod` / `SongRow.local` 每首歌都带，
`downloaded_song_ids()` 核对文件）。而「本地已下载」管理器回答的是同一个问题
——"这首歌本地有没有"——只是换了个切法（按**来源歌单**分组）。同一件事在
两页各说一遍、说法还不完全一样，几次 bug 都出在这儿。

**净删约 2000 行**：

| 删除 | 行数 |
| --- | --- |
| `download_page.dart` 的 `_LocalTab` + 标签栏 | 1137 → **394** |
| `src/ipod_web/routes/downloads.py` | −307 |
| `tests/test_web_routes_downloads.py` | −401 |
| `models.dart` 的 LocalTrack/LocalGroup/LocalTrackPage | −159 |
| `client.dart` 三个方法 → 一个 | −29 |
| `download_page_test.dart` 本地用例 | 1100 → 422 |

#### 「删除本地那份」没丢，挪了位置

原来是 `/api/downloads/remove`。`downloads.py` 整个删掉之后没接口了，所以
搬进 settings 的本地缓存那一组（跟 `/api/cache`、`/api/cache/clear` 一起，
它们管的是同一件事）：**`POST /api/cache/remove`**。删除逻辑逐行照搬。

界面上跟下载/同步放在同一处（歌单页）：右键单首 + 多选操作条一个红按钮
（排在最后、不跟下载/同步挨着，手滑代价不一样）。走确认框，明写
"iPod 上已经同步进去的歌不受影响"。

清空全部（含不在任何歌单里的孤儿缓存）走**设置 → 本地缓存**——那个入口
一查发现**早就有**了，不用新写。

#### 三态改名（里层也一起对齐）

`未处理` → **未下载**、`已在 iPod` → **已同步**、`已下载未同步` → **已下载**。

改名不止是表层：`skip_reasons` 的键会显示在规划预览对话框里，界面上写
"已同步"、弹窗里写"已在 iPod 上"就是自相矛盾，所以后端措辞一起改了。
`SongFilter.value` 一律没动——那是跟后端的协议。

第四种情况（同步过、本地那份已删）做成**后缀**：`已同步 · 本地无`。
状态数保持三个，但不把"本地没了"藏起来（上一轮就因为这个出过 bug）。

#### 歌单页补搜索（服务端筛）

删掉本地管理器后，整个应用没有"按歌名/艺人找"的地方了。补上，
**在服务端筛**：

```
GET /api/playlists/{id}/songs?search=陈粒
```

本地筛只能筛当前页那 50 首，246 首的歌单"搜了跟没搜一样"。搜索与状态筛选
**叠加**；`counts` 仍是**整单**的概况（跟着搜索跳的话顶上那行就废了）。

#### 真机验证

```
三态    共 246 首 · 未下载 242 · 已下载 1 · 已同步 3
搜索    「陈粒」→ 2 首（虚拟、小半）；ASCII 大小写不敏感
叠加    search=大石&status=downloaded → 1 首
删本地  虚拟 → 「已同步 · 本地无」；**iPod 上 4 首一个没少**
往返    重新规划 needs_fetch=1 → 下回来 → 回到「已同步」
```

**测试**：Python 566 → **555**；Flutter 87 → **71**（删掉的都比新增的多）。
